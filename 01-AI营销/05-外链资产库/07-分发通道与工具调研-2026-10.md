# 分发通道与工具调研：Medium API/MCP + 一键分发（2026-10）

> 定位：[06-可发文章平台矩阵-2026Q4](./06-可发文章平台矩阵-2026Q4.md) Top5（Medium/WordPress.com/Tumblr/Instructables/BuzzFeed）的**自动化通道专项调研**。回答两个问题：①Medium 有无免登录发布通道（API/MCP/变通）②"一次写作→多平台发布"有无开源版或现成工具。结论：Medium 免登录通道不存在，Top5 无现成一键工具可覆盖，推荐 2 API 直连 + 2 浏览器/手工 的自研组合。
> 验证日期：2026-10-12。方法：WebSearch + GitHub Search API（curl）+ Wayback Machine CDX + 端点实测（curl）。
> 来源分级：**[O]官方 / [I]行业 / [C]社区**，未标注的为推断。链接均为本次验证时可达的原始出处。

## 一、Medium 通道现状（问题①）

### 1.1 官方 API：新 integration token 已彻底停发（半冻结传闻证实为"对新申请全冻结"）

| 验证点 | 结果 | 证据 |
|--------|------|------|
| 开发者门户 | **已下线**：developers.medium.com 301 重定向 → medium.engineering（Medium 工程博客，与 API 无关） | 本次 curl/WebFetch 实测 [O] |
| API 文档仓库 | [Medium/medium-api-docs](https://github.com/Medium/medium-api-docs) **2023-03-02 归档只读**，README 置顶警告 "The Medium API is no longer supported. We do not recommend using it."，2.3k★ | GitHub 实查 [O] |
| 新 token 政策 | 官方帮助中心口径："Medium will not be issuing any new integration tokens for our API and will not allow any new integrations. All existing tokens will continue to work." | help.medium.com 经搜索快照引用 [O]，多平台交叉印证：Make.com 社区 2024-12（"only works if you created a token in the past"）、n8n 文档 2026-06 更新 [C/I] |
| 官方帮助文章存亡 | help.medium.com 的 Publishing-API 文章（articles/213480768）**2020-01-16 起 404**（Wayback CDX 快照序列：2018-2019 多次 200 → 2020-01 起 404/403） | Wayback CDX 实查 [O] |
| API 端点基础设施 | 仍响应：`GET api.medium.com/v1/me` 无 token 返回 401（非 404/DNS 失效）——**存量 token 大概率仍可写**，与官方"existing tokens will continue to work"口径一致 | 本次 curl 实测 [O] |

**结论（1.1）**：对 2023 年后注册的**新 Medium 账号，官方 API 写入通道不存在**——设置页的 Integration Tokens 入口已随新申请关闭而失效。存量 token 有效但与老账号绑定，不可转移。

### 1.2 Medium MCP：有两个 GitHub 项目，路线分为 token 依赖与浏览器自动化

GitHub Search API 实查（`q=medium mcp`，按 star 排序，2026-10-12）：

| 项目 | Star | 最后 push | 技术路线 | 对新账号可用性 |
|------|------|-----------|----------|----------------|
| [Dishant27/medium-mcp-server](https://github.com/Dishant27/medium-mcp-server) | 28★ | 2025-04-06 | TypeScript，包装官方 Medium API | ❌ 依赖 integration token，新账号拿不到 token |
| [jackyckma/medium-mcp-server](https://github.com/jackyckma/medium-mcp-server) | 12★ | 2025-07-08 | **Playwright 浏览器自动化**，无需任何 token：首跑开可见浏览器手工登录一次 → session 存 `medium-session.json` → 之后无头复用 | ✅ 可用（但本质=浏览器自动化，与自研 CDP 同构） |
| [jignesh88/medium-mcp-api](https://github.com/jignesh88/medium-mcp-api) | 6★ | 2025-03-16 | API 包装 | ❌ 同 Dishant27 |

**jackyckma 项目深评**（README 实读）：
- 5 个工具：`publish-article`（标题+markdown+tags，可选草稿模式）/ `get-my-articles` / `get-article-content` / `search-medium` / `login-to-medium`
- 坑点自述：作者声明"AI（Claude/Cursor）数小时开发"，操作慢（10-30s/次），Medium 改 UI 选择器即碎，Google 登录 session 存不住（须邮箱密码登录）
- 定性：**维护弱（12★、最后 push 距今 15 个月）、可靠性与自研 CDP 相当**——价值不在"更稳"，在于把浏览器发布封装成了标准 MCP 工具调用（Claude 会话内一句话发文章，省掉 CDP 脚本维护）。git 一次后按需魔改（选择器/发草稿再人审）是合理用法。

**结论（1.2）**：Medium MCP 存在，但**没有一条免登录/非浏览器路线**。token 系 MCP 全部对新账号死路；浏览器系 MCP 唯一可用项是 jackyckma（弱维护）。

### 1.3 变通通道逐条排查：secret email / RSS / import

| 变通通道 | 排查结果 | 证据 |
|----------|----------|------|
| **secret email 投稿地址**（传闻：每人一个 xxx@medium.com 投稿即发） | **查无此通道**。①help.medium.com 全库文章 URL 扫描（Wayback CDX，`articles/*email*` 与 `articles/*publish*` 两次全量过滤）——**无任何 "email publishing"/"post by email" 标题文章**，全部命中项为邮件通知/偏好设置类；②2025-2026 第三方（指南/Reddit/教程）零引用存活；③仅历史模糊印象，无官方文档佐证 | Wayback CDX 实查 + WebSearch 多轮 [C，负证据] |
| **RSS 导入发布** | **官方教程实为 IFTTT 集成**：help 文章 [236064187-Publish-to-Medium-from-an-RSS-Feed](https://help.medium.com/hc/en-us/articles/236064187-Publish-to-Medium-from-an-RSS-Feed)（2017 快照原文实读）教的是 "RSS feed → IFTTT applet → Medium Create a post"——而 IFTTT 的 Medium action 走**同一套官方 API**，新集成同样被冻结 | Wayback 2017 快照全文 [O] |
| medium.com/import（URL 导入为草稿） | 端点被 Cloudflare 拦（curl 403，无法免登录验证）。该工具为浏览器内单篇 URL 导入（迁移场景），非 API，且导入为草稿仍需人审发布 | 本次 curl 实测 + 功能定性 [O/推断] |
| api.medium.com 端点 | 基础设施活着（401 响应），存量 token 持有者可继续用 | 本次 curl 实测 [O] |

**结论（1.3）**：secret email 通道判定**不存在或早已无痕下线**（负证据充分）；RSS 路线本质是 IFTTT→API 中转，对无 token 账号同样死路。若要终验 secret email：登录 Medium → Settings → Publishing 页 1 分钟人工确认（唯一残留可能）。

### 1.4 Medium 最终判定

**免登录发布通道 = 无**。三选一：
1. **维持自研 CDP**（现状）——已验证可跑，掌控选择器；
2. **引入 jackyckma/medium-mcp-server 作 MCP 封装层**（fork 后魔改）——把 CDP 脚本换成标准 MCP 工具调用，Claude 会话直发，维护面更小；
3. ~~API token~~——新账号此路不通，不必再投入验证。

（2 与 1 同为浏览器自动化，风险面相同：反自动化检测、选择器漂移；区别仅在工程形态。）

**开源格局两个硬结论**：
1. **博客向开源分发工具全部小众**（≤55★）且平台组合锁死在技术博客三件套（Medium/dev.to/Hashnode）——与 cushionmill Top5 重叠仅 Medium 一个，而恰恰这一个是工具们集体过不去的（token 依赖）。
2. 唯一大体量项目 Postiz 是社媒调度器（Buffer 替代品），博客平台零覆盖。**"一次写作→Top5 全发"的开源轮子不存在。**

## 三、推荐组合（问题②结论）

**没有"一键"工具能吃下 Top5；正解是 2+2+1 自研组合**：

| 通道 | 平台 | 方式 | 工程量 |
|------|------|------|--------|
| **API 直连**（优先全自动化） | WordPress.com | **v1.1 REST**（`public-api.wordpress.com/rest/v1.1/sites/cushionbench.wordpress.com/posts/new`）+ OAuth2 token——站点 cushionbench.wordpress.com 已建+Launch（2026-10-12，见 06 §三.2） | 小（一次打通） |
| **API 直连**（优先全自动化） | Tumblr | API v2 + pytumblr（官方 SDK）——图文帖批量。**✅ 2026-10-12 已打通**（博客 customcushion，凭证入 .env，首篇已发） | 小（一次打通，已完成） |
| **浏览器自动化** | Medium | fork [jackyckma/medium-mcp-server](https://github.com/jackyckma/medium-mcp-server) 装 MCP，或维持现有 CDP——二选一，前者会话内调用更顺手；保留"发草稿→人审→发布"开关降低封号风险 | 中 |
| **低频手工** | Instructables | 无 API 且 ToS 敏感——维持 2-4 教程/月手工发布（本就低频，06 §二节奏不变） | 零 |
| **低频手工** | BuzzFeed | 无 API 且 ToS 禁自动化——维持 1-2 篇/月手工 | 零 |

**明确不做**：
- 任何依赖 Medium API token 的工具/服务（integrate-io、crier、shahednasser、Postevery 的 Medium 连接）——新账号死路，验证成本都不用付；
- secret email 通道的进一步投入——负证据充分，唯一残留动作是登录 Settings→Publishing 页 1 分钟目检；
- 引入 Postiz/Micro.blog/Postevery 等 SaaS 为 Top5 分发——平台组合不匹配，Medium 死结无解，月费无意义；
- Instructables/BuzzFeed 的浏览器自动化——频次低（手工 30 分钟/月内），ToS 风险收益比不成立（与 06 矩阵口径一致）。

**对 06 矩阵的回写建议**：06 §三启动步骤 2/3（WP.com REST、Tumblr API v2）与本调研一致无需改；Medium 步骤可补一句"自动化通道=浏览器系 MCP/CDP 二选一，API 通道已对关闭（2026-10 验证），勿再调研 token 路线"。
