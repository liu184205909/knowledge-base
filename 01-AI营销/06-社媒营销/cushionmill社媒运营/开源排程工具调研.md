# 开源排程工具调研：有没有"自带 Pinterest 凭证"的 Buffer 替代

> 调研日期：2026-10-08 | 前置文档：`批量排程架构方案.md`（已定案 agent 本地队列 + Buffer FB 线）、`pinterest-tools-调研.md`、`facebook-automation-调研.md`
> 触发问题：市面上有很多 Buffer 类甚至免费开源的——找 Pinterest+FB 支持的自托管方案，替代 Buffer $6/月或其免费档（10 帖队列不够）。
> 来源分级：**官方文档/明文** > 厂商文档 > 行业分析 > 社区讨论；GitHub 数据为本日 API 实测。

---

## TL;DR 决定性结论

1. **"工具自带 Pinterest production 凭证"的开源自托管方案 = 结构性不存在。** 逐一核查所有主流工具（Postiz/Mixpost/TryPost/……）：自托管版全部要求**用户自己创建 Pinterest App**（Postiz 官方文档明文要求填 `PINTEREST_CLIENT_ID/SECRET` 并"wait on the App to get approved"）。原因不是技术懒，是 Pinterest 的 app 审核/secret 与 app 所有者绑定——开源分发 production secret = 被滥用 = 被 Pinterest 撤销，没有项目敢这么做。**"零 API 门槛"只存在于 SaaS 托管版**（Postiz Cloud / Buffer / Mixpost hosted 用厂商自己的过审 app）。
2. **但"自己的 app"≠ 死路**：本库 10-07 已实测 **Trial token 可发 production pin**（见 `批量排程架构方案.md` §一）。若该实测成立，Postiz 自托管 + 自己的 Trial app = **免费 + 无限队列 + 图形界面** 的完整 Buffer 替代——与已定案的"agent 本地队列"走的是同一条 API 通道，只是多了管理 UI。⚠️ 冲突标注：Pinterest 官方 access-tiers 文档明文"Trial access 创建的 Pins/Boards 仅创建者可见（Sandbox 实体）"，与我方实测矛盾——**部署 Postiz 前先花 30 秒重验**（Trial app 发 1 条 pin，无痕窗口看公开可见性）。
3. **FB 线在一切自托管开源工具中都是死路**：它们接 Facebook Page 同样要求用户自建 Meta app + 审核 + Business 验证——而我方约束是**不能注册 Meta app**（`facebook-automation-调研.md` 红线）。所以无论选什么开源工具，**FB 线只能继续 Buffer**（免费档或 $6/月）。开源替代只对 Pinterest 线有意义。

## 一、发布通道机制拆解（选型的决定性维度）

### 1.1 为什么开源工具不可能自带 Pinterest 凭证

| 通道模式 | 凭证归属 | 谁在用 | 对我方意义 |
|---|---|---|---|
| **SaaS 自带凭证**（用户 OAuth 授权给厂商 app） | Buffer/Postiz Cloud/Mixpost hosted 的过审 app | Buffer、Tailwind、Postiz Cloud、Later | 零 API 门槛，但要月费/档位限制 |
| **自托管 BYO 凭证**（用户自建 app 填 key/secret） | 我方自己的 Pinterest App（Trial） | Postiz 自托管、Mixpost Pro、TryPost、n8n | 免费，但回到"自己的 app"→ 卡在 Trial 权限问题 |
| **UI 自动化**（Selenium/CDP 操控网页版） | 无需 API key | PinterestBulkPostBot、各类脚本 | 无 API 门槛，但风控/封号风险（FB 端已被反自动化打死） |

结构性原因（推断，基于平台政策）：Pinterest App secret 与 app 所有者绑定，审核时要求声明用途与 redirect URI；开源项目把 secret 打进代码 = 任何人可提取滥用 = app 被 Pinterest 撤销 + 违反 ToS。GitHub 全扫描未发现任何 star>100 的例外。

### 1.2 Pinterest API 权限层级：官方口径 vs 我方实测

| 口径 | 说法 | 来源级别 |
|---|---|---|
| **官方明文** | "All Pins and Boards created with Trial access are only visible to their creator as Sandbox entities"——Trial 发的 pin 是沙盒实体，仅创建者可见，非公开发布；真实发布需 Standard access（app 审核批准） | developers.pinterest.com/docs/key-concepts/access-tiers/（官方） |
| **社区佐证** | n8n/Make 社区："Trial access 下 POST /v5/pins 受限，pins 仅自己可见"；Trial→Standard 审核数天到数周，通过率看用例说明 | 社区讨论 |
| **我方实测（10-07）** | **Trial token 已实测可发 production pin**（agent 本地队列方案的立足点） | 本库实测（`批量排程架构方案.md` §一） |

处理纪律：实测 > 官方文档的政策口径（政策可能只对新 app/特定 scope 生效，或文档滞后）。但两者矛盾未消除，**任何基于 Trial 的新部署前先做 30 秒可见性重验**。

### 1.3 Facebook Page 的死结（不变）

所有自托管开源工具接 FB Page 都要求：自建 Meta app → App Review → Business Verification。我方不能注册 Meta app（既定约束），故 **FB 线唯一可行中间商 = Buffer**（已过审，$6/月或免费档）。Postiz 自托管解决不了 FB。

## 二、候选工具逐一核查（2026-10-08 GitHub API 实测）

### 2.1 Postiz（gitroomhq/postiz-app）——唯一值得部署的候选

| 维度 | 实测数据 |
|---|---|
| Stars / 活跃度 | **36,869 stars**，7.1k forks，3,302 commits，**本日仍在推送**（全类目第一梯队） |
| License | AGPL-3.0（自用无碍，改源码分发才触发） |
| 平台支持 | 30+ 网络：Pinterest ✅、Facebook ✅（Page）、IG/TikTok/X/LinkedIn/Threads/Reddit/Bluesky/Mastodon/Discord/Telegram… |
| **Pinterest 通道** | **BYO 凭证**：要求 Pinterest **公司/商业账户** + 自建 Pinterest App（`PINTEREST_CLIENT_ID`/`PINTEREST_CLIENT_SECRET`）+ OAuth 回调 `/integrations/social/pinterest`。官方文档明文要等 app 审批。**不自带凭证** |
| FB Page 通道 | BYO：自建 Meta app + 审核 → **我方死路** |
| 部署要求 | Docker Compose **6-9 个容器**（app + PostgreSQL + Redis + Temporal + Elasticsearch）；官方最低 **2 vCPU / 2GB RAM / 20GB 盘**（2GB 实测可跑），推荐 4GB / 50GB。VPS 现有资源满足；本地 Windows 走 Docker Desktop 亦可但常驻内存吃紧 |
| 队列能力 | 无限（自托管无档位限制） |

### 2.2 Mixpost（inovector/mixpost）——Lite 停更，Pinterest 在付费版

| 维度 | 实测数据 |
|---|---|
| Stars / 活跃度 | 3,787 stars，MIT；**Lite 开源仓最后推送 2026-03-16（停更近 7 个月）**——精力已转向 Pro/Enterprise 付费仓（其 App 仓 2026-09-29 仍活跃）。open-core 模式，免费版被战略性放弃的信号 |
| Pinterest | **仅在 Pro 版**（一次性付费闭源/源码付费下载），Lite 免费版平台清单不含 Pinterest；Pro changelog 近期才加 Pinterest 视频发布 |
| 通道 | 同为 BYO 凭证（自建 Pinterest app） |
| 结论 | **排除**：免费版没 Pinterest，付费版才解锁 → 比起 Postiz（AGPL 全功能免费）无任何优势，且主线停更 |

### 2.3 TryPost（trypostit/trypost）——新但小

679 stars，2026-01 创建，本日活跃，Laravel+Vue，AGPL-3.0，12 网络含 Pinterest，自带 MCP server + REST API（对我们 agent 线友好）。集成文档模式与 Postiz 相同：admin 在各平台 console **自建 app 填 client id/secret**——BYO 凭证，无例外。风险：10 个月项目、社区基数小，长跑稳定性不如 Postiz。**备选观察**。

### 2.4 GitHub 全扫描其余候选（star>500 或场景对口）

| 项目 | Stars | 判定 |
|---|---|---|
| brightbeanxyz/brightbean-studio | 2,418 | 自托管社管平台，2026-09 活跃；同类 BYO 凭证模式，生态远弱于 Postiz，不单独深挖 |

| n8n 自建管线 | — | Pinterest node 同样走 v5 API + BYO OAuth —— 与直接调 API 同权限约束，无增益 |

### 2.5 例外路径：Postiz Cloud（托管版=Buffer 模式，但更贵）

Postiz Cloud 用 Postiz 自家过审 app（**真·零 API 门槛**），Pinterest 全档可用。但：免费档 **50 帖总量**（一次性，比 Buffer 免费档更抠）；Standard **$29/月 5 channels**——是 Buffer Essentials（$6/频道/月）的 ~5 倍价。结论：**Postiz Cloud 无性价比，不如 Buffer**。

## 四、Buffer 免费档够用性判定（542 条素材场景）

官方口径核实（buffer.com/pricing + Help Center，2026-10）：

- 免费档 = **3 channels + 每频道 10 条"排队中"帖 + 1 用户**。限制是**队列深度**不是月总量——帖发出后槽位释放，**月发帖量实际无限**。
- **CSV bulk 免费档可用**：每频道每上传 10 条（受队列槽位约束）；付费档 100 条/次、队列 5,000。
- 隐藏限制：**终身只能绑 8 个不同频道**（lifetime unique channels），不能无限换绑。

套我方节奏（`批量排程架构方案.md`：Pinterest 3-4 条/天、FB 1 条/天）：

| 线 | 免费档表现 | 判定 |
|---|---|---|
| **FB Page（1/天）** | 10 帖队列 = **10 天补一次**，每次 CSV 传 10 条 | ✅ **完美够用**——FB 线可省掉 $6/月 |
| **Pinterest（3-4/天）** | 10 帖队列 = **每 3 天补一次** × 542 条全周期 ~160 次 | ⚠️ 能跑但摩擦大——"免日常关注"诉求下不合格 |

结论：**免费档只够 FB 线**；Pinterest 主力线三选一（见下）。

## 五、最终路径判定

```
FB 线（定案不变）
  └─ Buffer 免费档（10 帖队列 × 1/天节奏 = 10 天补一次，$0）——或维持 Essentials $6/月图省事

Pinterest 线（三选一，按 Trial 重验结果分流）
  ├─ 路径 A（已定案默认）：agent 本地队列（JSON + Windows 计划任务 dispatcher）——零部署、零 UI，Trial token 直发
  ├─ 路径 B（要图形界面/多频道日历管理时）：Postiz 自托管 @ VPS（2GB RAM，6-9 容器）
  │    └─ 前置门：30 秒 Trial 重验（发 1 条 pin → 无痕窗口查公开可见性）
  │       ├─ 可见 → 部署可行，与路径 A 同通道，纯管理体验升级
  │       └─ 不可见（官方 sandbox 口径应验）→ 全部自托管开源同死，Pinterest 线只剩路径 A 若其仍活/Buffer $6/Sandard 重提
  └─ 路径 C（API 全线被堵的最后手段）：PinterestBulkPostBot 类 Selenium 批量（无定时、封号风险，自担）
```

**一句话总判**：开源世界里"像 Buffer 一样零门槛用 Pinterest"的东西不存在——自托管开源只是把 API 门槛从"厂商的 app"换成"你自己的 app"；既然我们已有 Trial 通道（实测可发），这个门槛实际为零，Postiz 自托管是纯管理体验升级项而非刚需，**默认路径仍是已定案的 agent 本地队列 + Buffer FB 线**。
